1장 DB 개요

  • 파일시스템의 문제 6가지: 데이터 종속성, 무결성 침해, 중복성, 불일치, 표준화 어려움, 보안성 결여
  • DB의 장점: 데이터 독립성, 무결성 유지, 중복·불일치 최소화, 표준화 용이, 높은 보안성, 공유 용이
  • DB = 데이터의 집합 / DBMS = 이를 관리하는 S/W. 응용프로그램은 반드시 DBMS를 통해 접근한다.

2장 정보시스템 구축과 DB 설계

  • 모델 = 현실세계를 개념화·단순화하여 가시적으로 표현한 것 / 모델링 = 모델을 만드는 과정 = 추상화
  • DB에는 개체(entity)의 정보가 반영되고, 행위·사건(behavior/event)은 프로그램에 반영된다.
  • 구축 절차: ISP → 업무분석 → 데이터모델링 / 프로세스모델링 → 상관모델링(CRUD 매트릭스) → 물리 DB설계 → DB구축 → 개발·테스트 → 튜닝 → 유지보수

DBMSDBMS 종류와 무관특정 DBMS를 염두

O/X

  1. 논리적 설계는 Oracle/MySQL 등 제품을 먼저 정하고 진행한다 → X
  2. 반정규화는 물리적 설계에서 수행한다 → O
  3. 인덱스 설계는 논리적 설계 단계의 작업이다 → X
  4. 데이터 모델링의 최종 산출물은 ERD이다 → O
  5. 개체의 행위·사건도 DB 설계에 반영된다 → X
  6. 주식별자는 null 불가, 외래식별자는 null 가능 → O
  7. 1:1 관계의 두 엔티티는 하나로 합칠 수 있다 → O
  8. M:N 관계는 완성된 관계이다 → X

3장 모델링 주요 개념

  • 엔티티: 업무의 관심 대상이 되는 정보를 가진 유형·무형의 사물
  • 분류 5가지: 유형(고객, 사원) / 무형(생산계획, 부서조직) / 문서(주문서, 거래명세서) / 이력(입고이력) / 코드(국가코드)
  • 엔티티 조건: ① 업무에 필요하고 관리할 정보 ② 인스턴스 2개 이상 ③ 속성 1개 이상
  • 명명: 현업 용어, 약어 지양, 단수 명사, 유일, 생성 의미대로
  • 속성: 더 이상 분리되지 않는 최소 단위 데이터 → 테이블의 컬럼
  • 속성 3분류: 기본속성(현실에서 얻음) / 설계속성(코드, 일련번호) / 유도속성(금액 = 수량 × 단가)
  • 관계: 두 엔티티 간 의미 있는 연결 = 공유하는 속성이 있다는 뜻 (이름은 달라도 됨)
  • 카디널리티 = 최대 참여수: 단일 |, 다중 <
  • 참여도 = 최소 참여수: 필수 |, 선택 O
  • 대부분 1:N / 1:1은 합칠 수 있음 / M:N은 미완성 → 해소 필요
  • 부모-자식: 정보가 먼저 생성되는 쪽 = 부모. 일반적으로 1:N, 부모 쪽 필수 : 자식 쪽 선택
  • 부모의 주식별자 → 자식의 외래식별자

4장 ERwin

  • CASE 도구: 분석·설계·구현·테스트 전 과정 + 문서화 지원. 데이터설계도구 기능: 논리 모델링, 물리 모델링, DB 자동 구축, 역공학
  • ERD 4가지 레벨: ① 엔티티 레벨 ② 주식별자 레벨 ③ 식별자 레벨 ④ 속성 레벨
종류의미선
식별 관계FK가 자식 PK의 일부실선
비식별 관계FK가 PK와 별도(일반 속성)점선
M:NFK 추가 안 됨, 정보만 표시—
  • 관계 맺을 때 부모를 먼저 클릭 → 자식 클릭. 부모 PK가 자식 FK로 자동 추가
  • ERwin 기호: "one or more" = P, "zero or one" = Z
  • 업무규칙은 관계선 → RI Actions 탭에서 Parent/Child × Insert/Update/Delete Rule 지정

5장 업무분석

  • 분석 단계의 작은 오류가 누적 → 눈덩이 효과
  • 준비: 회사 이해 → 서브젝트 에어리어 분할 → 문서 수집 → 담당자 인터뷰 → 정리
  • 수집 문서: 업무매뉴얼 / 다른 업무주체와 주고받는 문서(거래명세서) / 고유업무 문서(입고전표 — 담당자에게 직접 받아야 함)
  • 인터뷰 필요성: 문서만으로 불충분, 불명확한 점 해소, 중요/비중요 정보 분리, 현재 문제점은 실무자가 가장 잘 앎
  • 인터뷰 대상: 데이터·업무 → 일선 담당자, 의사결정·경영 → 중간관리자
  • 인터뷰 시간: 1시간 이내, 여유 있는 시간대 / 질문은 사전에 공지하고 문서화
  • 주의: 대상자는 소극적 → 주도적 진행(잡담·하소연 방지), 편안한 분위기, 민감한 사안 신중

6장 엔티티 정의

  • 데이터 모델링의 핵심 = 엔티티 도출. 정해진 공식은 없음
  • 도출 소스: 업무기술서, 인터뷰, 장부·전표, 기존 시스템 산출물, DFD의 Data Store, 현장 견학

일반적인 도출 순서 (7단계)

  1. 엔티티 후보 풀과 엔티티 리스트(엔티티명/포함속성/유사어) 준비
  2. 문서에서 명사 표시
  3. 명사 분류: 엔티티 → 엔티티명 / 속성 → 포함속성 / 인스턴스 → 소속 엔티티 / 불분명 → 후보 풀
  4. 중복·유사 명사 통합 (고객, 회원 → 회원)
  5. 후보 풀 재검토 → 리스트로 옮기거나 제외
  6. 시스템에서 관리할 필요가 있는지 검토 (회원카드·월말결산 제외)
  7. 엔티티 기술서 작성 (엔티티명 / 설명 / 관련속성 / 유사어 / 비고)
  • 후보 구분 기준: 속성 1개 이상? 인스턴스 2개 이상? 업무상 관리 필요? 속성을 못 찾으면 → 다른 엔티티의 속성
  • 장표명 대신 엔티티다운 이름: 입고전표 → 입고내역
  • 다른 전표에도 반복 등장하는 항목을 별도 엔티티로 추출 (업체 → 공급처, 제품 → 제품정보)

헤더/상세를 구분해야 하는 이유

판매전표 한 장 = 헤더 1건 + 상세 N건

  • 한 엔티티로 두면 반복 그룹이 생겨 품목 수만큼 헤더 정보가 중복 저장되고, 수정 시 불일치와 삽입/삭제 이상이 생긴다.
  • 몇 개 품목이 올지 몰라 컬럼 수를 정할 수 없다 (제품1, 제품2, …).

7장 식별자·관계·속성 정의

  • 주식별자: 인스턴스를 구분하는 기준 속성. 현재뿐 아니라 미래에도 중복이 없어야 함. 확인 방법 = 테이블을 그려본다
  • 복합 주식별자: 일일판매실적 = 판매일자 + 제품번호
  • 마땅한 주식별자가 없으면 → 인위적 주식별자 일련번호
  • 인위적 주식별자의 문제점: 같은 전표를 두 번 입력해도 들어감 → 내용상 중복
  • 최소성: 주식별자는 최소한의 속성으로 구성. 검토법: PK 속성을 하나씩 빼봤을 때도 유일성이 유지되면 그 속성은 불필요 → 제거
  • 관계 정의 방법: ① 문서에서 동사 찾기 ② 관계 매트릭스 ③ 부모·자식 찾기 (A를 만들려면 B 정보가 필요 → B가 부모) ④ 카디널리티·참여도 표시
  • 외래식별자 정의: 부모/자식 구분 → 부모 PK가 자식에 있는지 확인, 없으면 추가

Rule 1~4

  1. 관계 있음 = 공유 속성 있음
  2. 먼저 생성되는 쪽이 부모
  3. 부모의 공통속성은 PK, 자식의 공통속성은 FK
  4. 부모:자식 = 1:N (1쪽이 부모)

§2 ★ 참조무결성 (업무규칙)

업무규칙 = 관계 있는 두 테이블에서 한쪽 데이터 변화로 생길 불일치를 막기 위한 조치를 정의한 것

예시 데이터: 부서(101 영업부, 125 관리부, 146 생산1부, 150 생산2부), 사원(김철수 101, 홍길동 101, 강만길 125, 이재천 146)

부모 테이블 삭제/수정 규칙

규칙삭제수정
Restrict자식이 참조 중이면 삭제 불가 → 삭제 가능한 부서는 150뿐참조 중이면 수정 불가
Cascade자식도 함께 삭제 → 101 삭제 시 김철수·홍길동 삭제자식 FK도 함께 수정 (101→111)
Set Null자식 FK를 null로자식 FK를 null로
Set Default자식 FK를 미리 정한 기본값으로동일
None아무 조치 없음 (무결성 깨질 수 있음)동일

자식 테이블 삽입/수정 규칙

  • 부모에 없는 값(777)이면 삽입/수정 거부 + 에러 → Restrict
  • 자식 튜플 삭제는 부모에 아무 영향 없음

3가지 정책 비교

RestrictCascadeSet Null
무결성 보장 방식위반 연산 자체를 거부변경을 자식에 전파참조를 끊음
장점가장 안전, 실수로 인한 데이터 손실 방지일관성 자동 유지자식 데이터는 보존
단점자식을 먼저 정리해야 해서 번거로움의도치 않은 대량 삭제 위험FK가 NOT NULL이면 사용 불가
적합한 예대출 기록이 있는 회원 탈퇴 불가주문 삭제 → 주문상세도 삭제부서 폐지 시 사원은 남기고 부서만 미정
  • 도서관 회원 → 대출: Parent Delete = Set Null 또는 Restrict / Parent Update = Cascade / Child Insert·Update = Restrict / Child Delete = None
  • 판단 질문: "부모가 사라질 때 자식 기록을 보존해야 하는가?" → 보존 필요(이력·회계) → Restrict/Set Null, 종속 데이터 → Cascade
  • 부모 삭제인데 이력 보존 필요 → Restrict 또는 탈퇴여부 같은 논리 삭제 플래그

§3 ★ 유도속성

  • 정의: 다른 속성으로부터 계산·변형되어 나오는 속성 (금액 = 수량 × 단가, 합계금액, 누적구매금액)
  • 불일치 예: MP3 단가가 350 → 360으로 바뀌었는데 금액 3500을 고치지 않음 → 수량×단가(3600) ≠ 금액
  • 같은 정보가 두 군데 저장 = 중복 → 갱신 누락

저장 여부 판단 기준

저장하는 게 유리저장하지 않는 게 유리
계산 비용이 크고 조회가 매우 잦음계산이 간단함
원본 데이터가 거의 변경되지 않음원본이 자주 변경됨
당시 값을 이력으로 보존해야 함항상 최신 값이 필요
저장한다면 트리거/프로그램으로 동기화 방안 마련

판매상세의 단가는 제품의 현재 단가가 아니라 판매 당시 단가라서 저장 의미가 있다. 금액은 수량×단가로 계산 가능 → 유도속성.

§4 ★ 외래키 위치와 Null 여부

  1. FK는 항상 N쪽(자식)에 둔다.
  2. 1:1이면 나중에 생성되는/선택 참여하는 쪽에 둔다.
  3. M:N이면 교차 엔티티를 만들어 양쪽 PK를 모두 FK로 받는다.
  4. Null 여부 = 자식이 부모 관계에 필수 참여인가?
    • 사원은 반드시 부서 소속 → FK NOT NULL
    • 사원이 부서 미배정 가능 → FK NULL 허용
    • 식별 관계(FK가 PK의 일부) → 무조건 NOT NULL
    • Set Null 규칙을 쓰려면 FK가 NULL 허용이어야 함

§5 ★ 양쪽 최소·최대 참여수 표기

(최소, 최대) = (참여도, 카디널리티). 상대 엔티티 인스턴스 1개 기준으로 "나와 연결되는 개수"

예) "모든 사원은 반드시 하나의 부서에 소속된다. 부서는 사원이 없을 수도, 여러 명일 수도 있다."

부서 ||──────────O< 사원
부서 1개당 사원: (0, N) → 사원 쪽 끝에 O<
사원 1명당 부서: (1, 1) → 부서 쪽 끝에 ||
  • 안쪽 기호 = 최소(O 선택 / | 필수), 바깥쪽 기호 = 최대(| 단일 / < 다수)
  • 사원 쪽 FK 부서코드 → 사원이 부서에 필수 참여 → NOT NULL

연습

  • "사원은 주차카드를 최대 1장 받을 수 있다(안 받아도 됨). 주차카드는 반드시 한 사원에게 발급된다."
    사원 1명당 카드: (0, 1) → 카드 쪽 끝 O| / 카드 1장당 사원: (1, 1)
  • "주문 1건에는 제품이 최소 1개 이상, 제품은 주문된 적이 없을 수도 있다." → M:N → 주문상세로 해소
    주문 1건당 주문상세 (1, N), 제품 1개당 주문상세 (0, N)

§6 ★ 서술형: 화면 설계 기반 DB 구축의 문제점 3가지와 개선 절차

상황: 개발자가 화면을 먼저 설계하고 화면 항목을 그대로 테이블 컬럼으로 만든 경우

  1. 데이터 중복 → 불일치: 여러 화면의 같은 항목(고객명·주소)이 테이블마다 중복 저장됨
  2. 엔티티·관계·식별자 미정의: 헤더/상세가 섞여 반복 그룹 발생, 참조무결성 규칙이 없음
  3. 유도속성·화면 전용 항목의 무분별한 저장: 화면에 종속되어 확장성·유지보수성 저하

개선 절차

  1. 업무분석: 문서 수집, 인터뷰, DFD 작성 (화면이 아니라 업무와 데이터 기준)
  2. 엔티티 도출: 명사 추출 → 후보풀 → 통합 → 필요성 검토 → 기술서, 헤더/상세 분리
  3. 주식별자 정의: 유일성·최소성 검토
  4. 관계·외래식별자 정의: 부모/자식, 카디널리티·참여도, FK 위치·NULL 여부
  5. 업무규칙(참조무결성) 정의: Restrict / Cascade / Set Null
  6. 속성 상세화 → 정규화 → 통합·검증 → 물리 설계

§7 연습: ERD

A. 판매전표

  • 도출 엔티티 6개: 부서, 사원, 고객, 제품, 판매(헤더), 판매상세(상세)
  • 판매상세 PK = 판매번호 + 제품번호 (복합, 식별 관계). 같은 전표에 같은 제품이 두 줄 나올 수 있으면 순번 추가
  • 판매–판매상세: 판매 1건당 상세 (1, N) / 제품 1개당 상세 (0, N)
  • 유도속성 4개: 금액, 합계금액, 당월실적누계, 누적구매금액
  • 판매부서가 항상 사원의 소속부서면 판매.부서코드는 사원을 통해 유도되므로 중복 → 제거 검토

B. 도서관

  • 회원–도서는 원래 M:N → 대출이 교차 엔티티로 해소
  • 대출의 PK가 인위적(대출번호) → 대안 PK = 대출일 + 회원번호 + 도서관리번호
  • "미반납 도서가 있으면 탈퇴 불가" → 회원 삭제 Restrict 또는 탈퇴여부로 논리 삭제

C. 수강신청(학번, 이름, 전공, 과목1~3, 과목명1~3) 재설계

  • 문제점: 반복 그룹(과목1~3), 학생 정보 중복, 과목명 중복·불일치, PK 불명확
  • 재설계: 학생(◆학번, 이름, 전공) / 과목(◆과목번호, 과목명, 학점) / 수강(◆학번(FK), ◆과목번호(FK), ◆학기)

D. 오류 찾기 체크 포인트

  • FK가 1쪽(부모)에 들어가 있지 않은가?
  • M:N 관계가 해소되지 않은 채 남아 있지 않은가?
  • 1:1인데 합칠 수 있지 않은가?
  • 참여도가 업무 규칙과 맞는가? (필수인데 FK가 NULL 허용 등)
  • PK가 최소성을 만족하는가 / 미래에도 유일한가?
  • 다른 관계를 통해 유도 가능한 중복 관계/FK는 없는가?

§8 단답 암기 리스트

  • DFD 4기호: 데이터 저장소 / 프로세스 / 데이터 흐름 / 종단점
  • 인터뷰 질문 3유형: 열린 / 닫힌 / 추가
  • 속성 3분류: 기본 / 설계 / 유도
  • 데이터 모델링 3요소: 엔티티 / 관계 / 속성
  • 식별자 ↔ 키: 주식별자 - 기본키, 외래식별자 - 외래키, 보조식별자 - 대체키
  • 부모 삭제·수정 규칙: Restrict / Cascade / Set Null (+ Set Default, None)
  • 식별 관계 = 실선 = FK가 PK 일부 / 비식별 관계 = 점선

  • 데이터 흐름은 반드시 프로세스를 거친다 (종단점 → 저장소 직접 연결 X)

9-12. 독립 / 종속 엔티티

  • 독립 엔티티: 다른 엔티티의 PK를 빌리지 않고 자기 속성만으로 식별됨. ERwin에서 각진 사각형
  • 종속 엔티티: 식별 관계로 부모 PK를 자신의 PK 일부로 받음. ERwin에서 모서리가 둥근 사각형
  • 비식별 관계로 FK만 받는 엔티티(사원 → 부서코드)는 독립 엔티티

9-15. 주식별자 최소성

  • 수강(학번, 과목번호, 학기, 학생이름, 성적)의 PK가 학번+과목번호+학기+학생이름 → 학생이름은 불필요 (학번이 결정)
  • 학기를 빼면 재수강 시 중복 → 필요
  • 주식별자는 유일성(현재+미래)과 최소성을 모두 만족해야 함

9-16·20. 통합 ERD

  • 판매전표의 '제품번호·제품명'과 입고전표의 '제품코드·품명'은 같은 의미(유사어) → 제품 엔티티 하나로 통합
  • 각 전표는 헤더/상세로 분리, 상세는 식별 관계

9-17. 학과 삭제 시 가장 적절한 규칙

  • 학생 정보는 학과가 없어져도 보존해야 함 → Cascade는 부적절, Restrict(학생을 다른 학과로 옮긴 뒤 삭제)가 가장 적절
  • 학과 미배정을 허용하는 업무라면 Set Null도 가능
